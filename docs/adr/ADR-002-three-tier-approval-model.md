# ADR-002: 采用三级审批模型

| 字段 | 内容 |
|------|------|
| 编号 | ADR-002 |
| 标题 | 采用三级审批模型（标准/高危/紧急） |
| 状态 | 已采纳 |
| 日期 | 2026-08-16 |

## 上下文

LEVEE 的核心价值之一是"变更必须经过审批"（设计红线 R4：高危变更必须人工审批）。审批模型需要覆盖以下场景：

- 日常低风险变更（如重启服务、更新配置）需要轻量审批流程
- 高危变更（如删库、主从切换、防火墙全量变更）需要强审批与多审批人
- 紧急变更（如生产故障修复）需要快速通道但不能跳过审批
- 不可逆操作（irreversible: true）必须强制升高审批级别

可选方案：

1. **单级审批**：所有变更统一审批流程，简单但无法区分风险等级
2. **两级审批（标准/高危）**：区分日常与高危，但缺少紧急通道
3. **三级审批（标准/高危/紧急）**：按风险等级分级，紧急场景有独立通道
4. **自定义多级审批**：完全可配置，灵活但复杂度高，MVP 不宜引入

## 决策

采用 **三级审批模型**：标准（standard）/ 高危（high）/ 紧急（emergency）。

各级审批定义：

| 级别 | 触发条件 | 审批人要求 | 超时 |
|------|----------|------------|------|
| standard | 默认级别，workflow 未声明 high/emergency | 1 人通过即可，审批人不能是发起人 | 24h |
| high | workflow 声明 approval.level=high 或命中高危规则模板或含 irreversible: true | 2 人通过，审批人不能是发起人 | 4h |
| emergency | workflow 声明 approval.level=emergency | 1 人通过 + 事后补审，审批人不能是发起人 | 30min |

关键设计要点：

1. **一票否决**：任何审批人 reject 立即否决整个审批，无需等待其他审批人
2. **审批人隔离**：审批人不能是变更发起人（R4 红线）
3. **不可逆操作强制升级**：irreversible: true 的 step 自动将审批级别升至 high
4. **高危规则模板**：内置删库 / 主从切换 / 防火墙全量等高危规则，命中自动升级
5. **紧急事后补审**：emergency 级别允许快速通过但必须事后补审，确保审计闭环

## 后果

### 正面

- 覆盖 MVP 全部审批场景：日常变更轻量审批，高危变更强审批，紧急变更有通道
- 不可逆操作自动升级审批级别，防止高危变更绕过审批
- 一票否决语义简单明确，审批流程不会因部分人通过而绕过反对意见
- 紧急通道不跳过审批，满足合规要求（事后补审）

### 负面

- 三级模型在 MVP 阶段足够，但 V1 可能需要更细粒度的审批策略（如按环境区分审批人）
- 紧急事后补审依赖人工执行，存在遗漏风险
- 审批超时后的默认行为（自动驳回）可能阻断紧急变更，需要运维团队关注超时配置

### 缓解

- 高危规则模板可配置，团队可根据业务调整触发条件
- V1 引入转授权机制，解决审批人不在时的代理审批问题
- 紧急事后补审通过通知机制（webhook）提醒 oncall 跟进
