# ADR-006: 失败语义五档模型

| 字段 | 内容 |
|------|------|
| 编号 | ADR-006 |
| 标题 | 失败语义五档模型（retryable/manual_retry/rollback/escalate/fatal） |
| 状态 | 已采纳 |
| 日期 | 2026-08-16 |

## 上下文

LEVEE 的设计红线 R7 要求"失败必须可定位"：每个动作产出结构化日志 + 目标机上下文快照，失败可重放。

在变更执行过程中，失败场景多种多样，不同失败需要不同的处理策略：

- 网络抖动导致 SSH 连接超时：可自动重试
- 目标机磁盘满导致写入失败：需人工介入清理后重试
- 前置步骤失败导致后续步骤无法继续：需回滚已执行步骤
- 回滚本身也失败：需升级通知 oncall
- 配置错误导致所有目标机必然失败：应立即终止避免扩大影响

可选方案：

1. **两档模型（成功/失败）**：简单但无法区分可恢复与不可恢复失败
2. **三档模型（重试/回滚/终止）**：覆盖主要场景但缺少人工介入和升级路径
3. **五档模型（retryable/manual_retry/rollback/escalate/fatal）**：精细区分失败语义，每种失败有明确处理策略
4. **自定义策略引擎**：完全可配置但复杂度高，MVP 不宜引入

## 决策

采用 **五档失败语义模型**，每种失败语义对应明确的处理策略。

| 档位 | 语义 | 触发条件 | 处理策略 | 示例 |
|------|------|----------|----------|------|
| retryable | 可自动重试 | 瞬态故障（网络超时 / 连接重置） | 自动重试，最多 3 次，间隔指数退避 | SSH 连接超时 |
| manual_retry | 需人工介入后重试 | 非瞬态但可恢复（目标机资源不足 / 依赖未就绪） | 暂停等待人工介入，人工修复后 `levee retry` 继续 | 目标机磁盘满 |
| rollback | 需回滚 | 步骤失败且影响已执行步骤（数据不一致 / 配置错误） | 自动触发回滚，按批逆序执行 rollback 步骤 | 配置写入导致服务异常 |
| escalate | 需升级 | 回滚失败或部分回滚 | 通知 oncall + 审批人，等待人工决策 | 回滚后验证失败 |
| fatal | 致命终止 | 不可恢复错误（配置错误 / 权限不足 / 哈希校验失败） | 立即终止所有批次，记录审计，通知发起人 | plan hash 不匹配 |

关键设计要点：

1. **失败语义由 step 声明**：每个 step 可声明 `on_failure` 策略，未声明则按默认规则推断
2. **默认推断规则**：shell / command 默认 retryable，file / pkg 默认 rollback，irreversible 默认 escalate
3. **批次级传播**：单目标机失败的处理策略影响整个批次（如 batch 中 50% 目标机 retryable 失败则整批重试）
4. **审计留痕**：每次失败处理（重试 / 回滚 / 升级）都记录审计 trace

## 后果

### 正面

- 精细区分失败语义，每种失败有明确处理策略，避免"一刀切"导致误操作
- retryable 自动重试减少人工介入，提高变更执行效率
- rollback 自动回滚减少故障半径，满足 R2 红线（变更必须可回滚）
- escalate 升级通知确保回滚失败时 oncall 及时介入
- fatal 立即终止避免不可恢复错误扩大影响

### 负面

- 五档模型增加引擎复杂度，失败处理路径从 1 条变为 5 条
- 默认推断规则可能不适用于所有场景，用户需显式声明 `on_failure`
- 批次级传播策略（50% 阈值）需要根据业务调整，MVP 采用固定阈值
- escalate 和 fatal 的边界有时模糊（如回滚失败是否应直接 fatal 而非 escalate）

### 缓解

- 默认推断规则覆盖 80% 常见场景，用户仅需对特殊场景显式声明
- 批次级传播阈值可配置，V1 支持按 workflow 自定义
- escalate 和 fatal 的边界通过审批模板明确：回滚失败默认 escalate，哈希校验失败默认 fatal
- 失败处理路径的单元测试覆盖所有五档场景，确保逻辑正确
