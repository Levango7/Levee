## 执行摘要

LEVEE 是面向非云原生基础设施的变更流水线引擎：把"改一台主机 / 数据库 / 网络设备 / 中间件"从手工命令和线性 playbook，升级为"计划 → 审批 → 分批执行 → 验证门禁 → 自动回滚 → 审计留痕"的完整闭环，默认无代理、CLI 优先。

与 ArgoCD / Flux 分层互补：ArgoCD / Flux 管 K8s 集群内（云原生层），LEVEE 管 K8s 集群外（非云原生基础设施层），各管一摊，企业同时使用可覆盖全资产变更治理。

核心价值链：定义变更（LEVEELang / 模板）→ 预检 → 审批 → 分批执行 → 验证 → 回滚 → 审计。

落地节奏：MVP（3 个月，单二进制零依赖，兼容层进首版保证"第一天能干活"）→ V1（6 个月，LEVEELang 编译期 / SLO 门禁 / 多通道）→ V2（12 个月，Agent 模式 / 事件驱动规则引擎）。

## 第1章 定位与边界

### 1.1 一句话定位

LEVEE 是面向非云原生基础设施的变更流水线引擎。

它把"改一台主机 / 数据库 / 网络设备 / 中间件"这件事，从 SSH 直连敲命令、Ansible 线性 playbook、堡垒机人工点选，升级为一条带计划、审批、分批、验证、回滚、审计的完整闭环流水线，且默认无代理、CLI 优先、可嵌入现有 CI / CD 与 ITSM。

### 1.2 为什么要和云原生层分开

云原生层（K8s 集群内）与非云原生基础设施层（K8s 集群外）在资源模型、变更语义、回滚机制、安全边界上存在结构性差异，强行用一套引擎同时管理两层会带来语义污染与责任模糊。

表：云原生层与非云原生基础设施层对照表

| 维度 | 云原生层（K8s 集群内） | 非云原生基础设施层（K8s 集群外） |
| --- | --- | --- |
| 资源模型 | 声明式 CRD / GitOps，最终一致 | 命令式动作 + 状态快照，过程可逆 |
| 变更单位 | manifest / Helm release | 主机配置、数据库 schema、防火墙规则、中间件参数 |
| 执行通道 | kube-apiserver（集群内） | SSH / WinRM / 厂商 API / Agent |
| 回滚机制 | 上一版本 manifest 重新 apply | 显式快照 + 按批逆序 undo |
| 幂等性 | 控制器调谐保证 | 需要在动作层显式实现 |
| 状态来源 | etcd | 主机文件系统 / 数据库 / 设备运行配置 |
| 失败半径 | 单 Pod / 单副本 | 单台主机 / 单库 / 单链路 |
| 审批语义 | 通常合并即生效 | 强人工审批 + 分批 + 验证门禁 |
| 典型工具 | ArgoCD / Flux / Helm | Ansible / SaltStack / 堡垒机 / 自研脚本 |

分开的原因：

1. 资源模型不同：云原生层是"声明 + 调谐"，非云原生层是"动作 + 快照"，强行统一会让 DSL 既要表达 desired state 又要表达 action sequence，语义膨胀。
2. 执行通道不同：云原生层走 kube-apiserver，非云原生层走 SSH / WinRM / 厂商 API，连接治理、限速、跳板机策略完全不同。
3. 回滚语义不同：云原生层回滚 = 重新 apply 旧 manifest，非云原生层回滚 = 按动作逆序执行 undo + 校验快照。
4. 安全边界不同：云原生层 RBAC 在集群内闭环，非云原生层必须穿越堡垒机 / 4A / 网络隔离区，凭据治理和审计链路独立。
5. 客户心智不同：云原生团队习惯 GitOps，传统运维团队习惯审批 + 分批 + 验证，强行统一会两边都不顺手。

### 1.3 与 ArgoCD / Flux 的关系

LEVEE 与 ArgoCD / Flux 是并列互补关系，不是替代关系。两者管辖层不重叠，企业可同时部署。

表：LEVEE 与 ArgoCD / Flux 对照表

| 维度 | ArgoCD / Flux | LEVEE |
| --- | --- | --- |
| 管辖层 | K8s 集群内 | K8s 集群外 |
| 资源模型 | GitOps + manifest | LEVEELang + 动作序列 |
| 执行通道 | kube-apiserver | SSH / WinRM / 厂商 API / Agent |
| 变更单位 | application / Helm release | workflow（含多 step、多 batch） |
| 回滚 | 上一 revision 重新 sync | 快照 + 按批逆序 undo + 回滚后验证 |
| 审批 | ArgoCD Approval / Flux 人工 sync | 内置三级审批（标准 / 高危 / 紧急） |
| 分批 | 不原生支持（需 Helm hook 模拟） | 一等公民，批次边界显式 |
| 验证门禁 | PostSync hook | 内置 4 类门禁 + SLO 时序 |
| 状态来源 | etcd | 内部 store + 目标机快照 |
| 无代理 | 不适用（集群内） | 默认无代理 |
| 典型场景 | 应用发布、配置同步 | 主机补丁、DB schema、网络策略、中间件参数 |

边界明确：

- LEVEE 不管 K8s 集群内资源（Pod / Deployment / Service / ConfigMap / CRD）。
- ArgoCD / Flux 不管 K8s 集群外资源（主机 / 数据库 / 网络设备 / 中间件）。
- 两者通过 webhook 互触：ArgoCD sync 完成后可触发 LEVEE 跑前置预检（如 DB schema 已就绪），LEVEE apply 完成后可触发 ArgoCD sync（如主机配置已变更，应用需重启）。

## 第2章 背景与动机

### 2.1 非云原生基础设施现状

非云原生基础设施仍是企业核心生产力的载体，尤其在金融、电信、制造、政企、能源行业，核心账务、核心网、工控系统跑在物理机 / 裸金属 / 传统数据库 / 专有网络设备上。

表：6 类资产现状与痛点对照表

| 资产层 | 典型变更 | 现状工具 | 痛点 |
| --- | --- | --- | --- |
| 计算层（物理机 / 虚拟机 / 裸金属） | OS 补丁、内核参数、sysctl、fstab、用户 / 组 | Ansible / 脚本 / 堡垒机 | 无审批、无分批、无验证门禁、回滚靠人记 |
| 存储层（SAN / NAS / 本地盘） | LVM、挂载、配额、FS 扩容 | Ansible / 厂商 CLI | 动作不可逆、无快照、误操作无回滚 |
| 网络层（路由 / 交换 / 防火墙 / LB） | ACL、路由策略、BGP 邻居、VIP | 厂商 CLI / NetBox + 脚本 | 配置语法异构、无统一 DSL、变更窗口硬约束 |
| 数据库层（MySQL / PostgreSQL / Oracle / Redis） | schema 变更、参数调优、主从切换、扩容 | 手工 SQL / pt-online-schema-change / 自研 | 大表 DDL 阻塞、无 SLO 门禁、回滚代价高 |
| 中间件层（Kafka / ZooKeeper / Nginx / Tomcat） | topic / partition / 配置 / 限流 | 厂商 API / 脚本 | 配置散落、无版本、无关联变更追踪 |
| 安全设备（IDS / IPS / WAF / 4A / 堡垒机） | 规则下发、策略变更 | 厂商 API / 人工 | 高危变更无门禁、审计断链 |

### 2.2 现有工具为什么不够

表：现有工具缺失项对照表

| 工具 | 强项 | 缺失项 |
| --- | --- | --- |
| Ansible | 无代理、模块化、生态成熟 | 无审批、无分批一等公民、无验证门禁、无 SLO 门禁、回滚靠 ignore_errors + 手写、无审计哈希链、线性 playbook 难表达批次边界 |
| SaltStack | 事件驱动、快 | Master 单点、无审批、无验证门禁、生态萎缩 |

| ITSM 工单 | 流程合规、审批留痕 | 不执行、与执行层断链、工单状态与实际变更状态不一致 |
| 自研脚本 | 贴合业务 | 不可维护、无审计、无回滚、人员单点 |

### 2.3 事故驱动

近年几起高影响事故都指向同一类根因：变更缺乏门禁、缺乏分批、缺乏回滚、缺乏审计。

表：事故与 LEVEE 对应设计对照表

| 事故 | 时间 | 根因 | LEVEE 对应设计 |
| --- | --- | --- | --- |
| GitHub 2023-05 数据库主从切换事故 | 2023-05 | MySQL 主从切换中 relay log 不一致，无切换前 SLO 门禁 | D4 验证门禁 pre_apply / post_batch / grace_period 三段时序，主从切换前强制 SLO 查询 |
| CrowdStrike 2024-07 蓝屏事故 | 2024-07 | 单批次全量下发通道规则，无分批、无金丝雀、无回滚 | D5 批次一等公民 + D4 不可逆操作标记 + 强制金丝雀批次 + 自动回滚 |
| 腾讯 AIOps 复盘（自愈误触发） | 多次 | 自愈规则误触发，扩大变更半径 | D6 自愈默认关、双触发显式开关、自愈变更走完整审批闭环 |

## 第3章 设计原则

### 3.1 继承的优点（从 Ansible）

LEVEE 不重新发明轮子，从 Ansible 继承以下已被验证的优点：

1. 无代理默认：通过 SSH / WinRM / 厂商 API 直连目标机，不在目标机常驻 Agent，降低入侵面与运维负担。
2. 声明式 + 幂等契约：每个动作模块声明 desired state，重复执行结果一致，幂等性由模块保证而非外层重试。
3. 模块化动作库：变更动作以 module 形式封装，可复用、可测试、可版本化，社区可贡献。
4. 标签选目标：通过 `--tags` / `--limit` / 主机清单 + 动态分组选择目标集，灵活圈选变更范围。
5. 推模式即时生效：变更由控制端主动推送，不依赖目标机轮询，生效时序可控。

### 3.2 八条设计红线

红线是 LEVEE 在任何迭代中都不能突破的硬约束，每条都有对应验收机制。

表：八条设计红线与验收机制对照表

| 编号 | 红线 | 验收机制 |
| --- | --- | --- |
| R1 | 默认无代理 | 首版不引入任何目标机常驻进程；Agent 模式（V2）作为可选增强，不作为默认 |
| R2 | 变更必须可回滚 | 每个 workflow 提交时强制带 rollback plan；不可逆操作显式标记并要求白名单 |
| R3 | 变更必须可审计 | 每次 apply 产出 trace + 哈希链，写入 WORM 存储，不可篡改 |
| R4 | 高危变更必须人工审批 | 高危 workflow 不允许 auto-approve，审批人不能是发起人 |
| R5 | 分批执行必须有验证门禁 | 批次间默认插入 post_batch 门禁，门禁失败阻断后续批次 |
| R6 | 语言必须类型安全 | LEVEELang 在编译期做类型检查，运行期不再做隐式类型推断 |
| R7 | 失败必须可定位 | 每个动作产出结构化日志 + 目标机上下文快照，失败可重放 |
| R8 | 兼容层不能污染核心 | 兼容逃生舱独立模块，不引入核心路径依赖，可独立卸载 |

## 第4章 核心设计 D1-D9 + D12

> 编号说明：D10（自愈触发器）和 D11（多集群联邦编排）在原 OpsChain 设计中存在，LEVEE 精简时移除——自愈与 LEVEE"变更流水线"定位不符（自愈是运行时闭环，非变更闭环），多集群联邦属于云原生层（ArgoCD/Flux 已覆盖）。详见附录B 精简移除清单。

### 4.1 D1 执行通道重做

#### 4.1.1 痛点

Ansible 的 SSH 通道在以下场景失效：

- 大规模并发时 SSH 多路复用抖动，连接复用率低。
- 网络隔离区需穿越跳板机，Ansible 的 ssh ProxyJump 在多跳场景配置复杂且不可观测。
- 交互式命令（如 `mysql >` 提示符、`vty` 配置模式）需会话级独占，连接池复用会污染会话状态。
- 厂商 API（如 F5 BIG-IP REST、华为 eNSP）非 SSH，Ansible 需写成 module，缺乏统一连接治理。

#### 4.1.2 机制

执行通道抽象为统一的 `Channel` 接口，下层按通道类型实现，上层编排逻辑不感知通道差异。

#### 4.1.3 连接池策略

连接池按通道类型区分策略，避免不同通道特性互相污染。

表：连接池策略对照表

| 通道类型 | 连接池策略 | 理由 |
| --- | --- | --- |
| SSH（非交互） | 连接池 + 多路复用（ControlMaster） | 命令无状态，复用安全 |
| WinRM | 连接池 + 单连接单命令 | WinRM 协议本身无多路复用 |
| Agent | 连接池 + 长连接 | Agent 维持心跳，复用降低握手成本 |
| 交互式 SSH（mysql / vty / config 模式） | 会话级独占，用完即弃 | 会话有状态（提示符、当前库、配置模式），复用会污染 |
| 厂商 REST API | HTTP 客户端连接池 + token 复用 | 标准 HTTP keep-alive |

#### 4.1.4 目标机抽象层

目标机抽象为 `Target` 接口，统一 5 类通道的连接、执行、收证、断开生命周期。

表：5 类通道及阶段对照表

| 通道 | 建连 | 执行 | 收证 | 断开 |
| --- | --- | --- | --- | --- |
| SSH | ssh handshake + auth | exec / shell | stdout + stderr + exit_code | close session |
| WinRM | WinRM negotiate + auth | run command | stdout + stderr + exit_code | close shell |
| Agent | register + heartbeat | dispatch task | task result | deregister |
| 厂商 API | token / session login | REST call | response body + status | logout |
| 交互式 SSH | ssh + pty | send + expect | prompt match + buffer | close pty |

#### 4.1.5 通道抽象层插件化

通道实现以插件形式加载，核心只依赖 `Channel` 接口，第三方可扩展新通道（如 IPMI、Redfish、自定义 4A 网关）而不修改核心代码。插件通过 `channel.yaml` 声明能力（并发上限、是否支持交互、是否需跳板机），编排器按能力调度。

#### 4.1.6 限速与背压

- 全局并发上限：可配置，默认 100 并发连接。
- 单通道并发上限：按通道能力声明，如交互式 SSH 默认 1。
- 单目标机并发上限：默认 1，避免对同一主机并发执行造成状态竞争。
- 背压：当连接池满或目标机响应超阈值，新任务排队而非拒绝，排队超时按 R7 产出结构化失败。

#### 4.1.7 目标可达性预检

apply 前强制做目标可达性预检：对每个目标机尝试建连 + 执行 `noop`，失败的目标机从批次剔除并产出预检报告，避免 apply 中途因连不上某台主机而批次半成功。

### 4.2 D2 语言与体验

#### 4.2.1 痛点

YAML playbook 在以下场景失效：

- 大型 workflow YAML 层级深，编辑易错，IDE 补全弱。
- 缺乏类型系统，变量类型在运行期才暴露错误。
- 条件、循环、批次边界用 Jinja2 模板字符串表达，逻辑与配置混杂，可读性差。
- 跨 workflow 复用靠 `include` / `import`，缺乏显式接口和参数契约。

#### 4.2.2 机制：类型化 DSL LEVEELang

LEVEELang 是 LEVEE 的工作流定义语言，定位为"类型安全的变更 DSL"：

- 静态类型系统：target / window / batch / step / approval 均有显式类型，编译期检查。
- 原生原语：batch / gate / rollback / pause 是一等原语，非模板字符串。
- 模块化：workflow 可声明 input / output，跨 workflow 调用走显式接口。
- 编译期：LEVEELang 编译为 IR（中间表示），IR 再由编排器执行，编译期可做影响面分析、冲突检测、plan 哈希锁定。

#### 4.2.3 变更克隆与模板实例化

- 变更克隆：对历史变更执行 `levee clone <run-id>`，生成可编辑副本，保留原参数与批次结构，用于"上次成功再来一次"。
- 模板实例化：模板带参数占位，实例化时填入具体值（如 `levee new db-migrate --params table=orders,batch_pct=10%`），编译期校验参数完整性。

#### 4.2.4 dry-run

`levee plan --dry-run` 不真正执行，只产出执行计划：目标集、批次划分、影响面、预估耗时、潜在冲突。dry-run 是审批前的前置动作，审批人基于 dry-run 报告决策。

#### 4.2.5 CLI 优先

所有操作均可通过 CLI 完成，不强制 Web UI。CLI 输出结构化（默认 human-readable，`-o json` 切换机器可读），便于嵌入 CI / CD 与脚本。Web UI 是 CLI 的可视化层，不引入 CLI 没有的能力。

#### 4.2.6 10 分钟测试门禁

PR 合并前强制跑 `levee test`，10 分钟内完成：单元测试（模块）+ 集成测试（对 mock target）+ Lint（LEVEELang 编译期）。超时即失败，避免长尾测试拖慢迭代。

#### 4.2.7 批次边界处理

批次边界在 LEVEELang 中显式声明，不靠运维心算：

- 按百分比：`batches: [10%, 30%, rest]`。
- 按数量：`batches: [3, 10, rest]`。
- 按标签：`batches: [{tags: [canary]}, {tags: [primary]}, {tags: [edge]}]`。
- 按主机分组：`batches: [{group: az-a}, {group: az-b}]`。

批次间默认插入 `post_batch` 验证门禁，门禁通过才进下一批。

### 4.3 D3 状态与漂移（简化）

#### 4.3.1 设计取舍

完整漂移检测（如 ArgoCD 的 sync status）在非云原生层代价高：目标机状态来源异构（文件系统 / 数据库 / 设备运行配置 / 内核参数），全量比对成本高且易误报。LEVEE 采取简化策略：

- 不做主动漂移检测：不周期性扫描目标机与 desired state 比对。
- 只读漂移报告：`levee drift report` 手动触发，对指定目标集做一次性比对，产出报告，不自动纠正。
- 显式删除：`remove` / `unmanage` 是显式动作，需走完整审批闭环，不做"发现漂移自动删除"。

#### 4.3.2 remove / unmanage 语义

- `remove`：从 LEVEE 管理范围移除目标机，并执行清理动作（如卸载已部署配置），需审批。
- `unmanage`：从 LEVEE 管理范围移除目标机，不执行任何动作，仅停止管理，需审批。

两者都产出审计记录，区别在于是否执行清理。

### 4.4 D4 变更闭环

变更闭环是 LEVEE 的核心，也是本设计最大章节。闭环覆盖从计划到归档的完整生命周期，每个阶段有明确输入、输出、失败语义。

#### 4.4.1 生命周期

```
plan → 审批 → apply → verify → (回滚 | 归档)
```

表：生命周期阶段输入输出对照表

| 阶段 | 输入 | 输出 | 失败语义 |
| --- | --- | --- | --- |
| plan | workflow + 目标集 + 参数 | 执行计划 + plan 哈希 + 影响面报告 | 阻断，不进审批 |
| 审批 | 执行计划 + 审批人 | 审批决策（通过 / 驳回 / 转授权） | 驳回则回 plan，超时按策略处理 |
| apply | 已审批计划 + plan 哈希 | 快照 + 执行 trace + 批次结果 | 按批次失败分级处理 |
| verify | 执行 trace + SLO 指标 | 门禁结果（通过 / 失败 / 超时） | 失败触发回滚或人工介入 |
| 回滚 | 快照 + 批次结果 | 回滚 trace + 回滚后验证结果 | 回滚失败升级人工 |
| 归档 | 全程 trace + 哈希链 | WORM 审计记录 | 归档失败告警，不阻断闭环 |

#### 4.4.2 plan 阶段

##### 4.4.2.1 目标预检

- 可达性预检：见 4.1.7。
- 权限预检：检查执行账号在目标机上的权限是否满足 workflow 声明的动作集。
- 依赖预检：检查 workflow 声明的目标机依赖（如主从关系、集群拓扑）是否满足。

##### 4.4.2.2 影响面分析

- 直接受影响目标机集合。
- 间接影响：如改主库影响从库、改上游 LB 影响下游服务、改 Kafka topic 影响消费者。
- 影响面报告随 plan 一并提交审批，审批人基于影响面决策。

##### 4.4.2.3 冲突检测

- 同目标机同时刻只能有一个 workflow 在 apply（互斥锁，见 4.5.4）。
- plan 阶段检查目标机是否有未完成的相关变更，有则冲突告警。

##### 4.4.2.4 动态目标集处理

目标集可静态声明（主机清单）或动态计算（如"所有 tag=primary 且 az=a 的 MySQL 主库"）。动态目标集在 plan 阶段物化为具体列表并锁定，apply 阶段不再重新计算，避免目标集在 plan 与 apply 之间漂移。

##### 4.4.2.5 plan 哈希锁定

plan 阶段产出 `plan_hash = hash(workflow + 目标集 + 参数 + 批次划分 + 影响面)`。审批基于此哈希，apply 前校验哈希一致，不一致则阻断（防止审批后偷偷改参数）。

#### 4.4.3 审批阶段

##### 4.4.3.1 分级

表：审批分级对照表

| 级别 | 触发条件 | 审批人要求 | 超时 |
| --- | --- | --- | --- |
| 标准 | 默认级别 | 任一有权限审批人 | 24h，超时驳回 |
| 高危 | 命中高危规则（如删库、主从切换、防火墙全量变更） | 至少 2 人审批，且不能是发起人 | 4h，超时驳回 |
| 紧急 | 紧急通道（如线上故障恢复） | 1 人审批 + 事后补审 | 15min，超时自动驳回并升级告警 |

##### 4.4.3.2 超时处理

超时默认驳回，发起人可重新提交。紧急审批超时升级告警（通知 oncall），不自动通过。

##### 4.4.3.3 驳回重提

驳回时需填写驳回理由，发起人基于理由修改后重新提交，新提交生成新 run-id，不复用旧 run。

##### 4.4.3.4 转授权

审批人可将审批权转授权给另一有权限人，转授权记录留痕，被转授权人不能再转授权（避免无限转）。

#### 4.4.4 apply 阶段

##### 4.4.4.1 哈希校验

apply 前强制校验 `plan_hash` 与审批时的哈希一致，不一致阻断。防止审批后 workflow 文件或参数被修改。

##### 4.4.4.2 快照创建

apply 前对每台目标机创建快照（按通道能力，如文件系统快照、数据库 logical backup、设备 running-config 备份）。快照是回滚的依据，快照创建失败则该目标机不进 apply。

##### 4.4.4.3 分批执行

按 plan 锁定的批次划分执行，批次间插入 `post_batch` 验证门禁。批次内并发执行（受 4.1.6 限速约束），批次间串行。

##### 4.4.4.4 主动暂停与恢复

- `levee pause <run-id>`：暂停当前 run，已完成批次保留，未开始批次不进。
- `levee resume <run-id>`：从暂停点恢复，不重跑已完成批次。
- 暂停 / 恢复留痕，需有权限操作。

##### 4.4.4.5 单台重跑

批次内某台失败可单独重跑：`levee retry-host <run-id> <host>`，不影响批次其他主机状态。重跑次数有上限（默认 3），超限升级人工。

##### 4.4.4.6 实时日志

apply 期间实时产出每台目标机的执行日志，CLI `levee logs <run-id> --target <host> -f` 跟随，Web UI 实时流。日志同时写入审计存储。

##### 4.4.4.7 目标机重启处理

部分变更（如内核参数、补丁）需重启目标机才生效。workflow 可声明 `requires_reboot: true`，apply 在该步完成后等待目标机重新可达再继续后续步骤，超时按失败处理。

#### 4.4.5 验证门禁

##### 4.4.5.1 四类门禁

表：四类验证门禁对照表

| 门禁类型 | 检查内容 | 时机 | 失败动作 |
| --- | --- | --- | --- |
| 命令门禁 | 在目标机执行检查命令，期望 exit_code / stdout 匹配 | pre_apply / post_batch / post_apply | 阻断后续 |
| SLO 门禁 | 查询外部 SLO 指标（错误率、延迟、可用性），期望在阈值内 | post_batch / grace_period | 阻断后续 + 触发回滚 |
| 探针门禁 | 调用外部探针端点（如健康检查、 readiness probe） | post_batch | 阻断后续 |
| 人工门禁 | 通知人工确认，等待人工通过 / 驳回 | post_batch（可选） | 超时按策略 |

##### 4.4.5.2 SLO 门禁时序

SLO 门禁分三段时序，覆盖变更前后全窗口：

1. `pre_apply`：变更前查询 SLO 基线，确认变更前系统健康，否则不开始变更。
2. `post_batch`：每批结束后立即查询，确认本批未引入异常，异常则阻断后续批次并触发回滚。
3. `grace_period`：所有批次结束后等待 grace period（默认 5min），再次查询，确认无延迟暴露的异常。

##### 4.4.5.3 重试与超时

- 门禁失败可配置重试（默认 3 次，间隔 10s），避免瞬时抖动误判。
- 重试全失败才判定门禁失败。
- 门禁整体超时（默认 5min），超时判定失败。

#### 4.4.6 回滚协议

##### 4.4.6.1 不可逆操作标记

部分动作天然不可逆（如 `DROP TABLE`、`DELETE FROM`、防火墙 `commit` 后的部分操作）。这类动作在 module 声明 `irreversible: true`，workflow 提交时强制要求：

- 进入白名单（显式允许该不可逆动作在该 workflow 使用）。
- 审批级别强制升高到高危。
- 不参与自动回滚（回滚协议跳过该动作，仅回滚可逆部分）。

##### 4.4.6.2 不受窗口约束

回滚不受原 workflow 的变更窗口约束。即使原窗口已关闭，回滚仍可执行，因为回滚是恢复安全状态，越快越好。

##### 4.4.6.3 白名单 + 快照 + 按批逆序

回滚执行策略：

1. 白名单：只有声明了 rollback plan 的 workflow 才可自动回滚。
2. 快照：按 apply 前创建的快照恢复。
3. 按批逆序：从最后一批向前逐批回滚，每批回滚后做回滚后验证。

##### 4.4.6.4 失败分级

表：回滚失败分级对照表

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| 回滚成功 | 所有批次回滚完成且验证通过 | 归档，通知发起人 + 审批人 |
| 部分回滚 | 部分批次回滚成功，部分失败 | 告警，升级人工，保留已回滚部分 |
| 回滚失败 | 回滚本身失败（如快照损坏） | 紧急告警，立即升级人工，停止自动动作 |

##### 4.4.6.5 回滚后验证

回滚完成后强制跑 verify，确认系统回到变更前状态。回滚后验证失败按回滚失败处理。

##### 4.4.6.6 人工确认归档

回滚完成后不自动归档，需人工确认（确认系统稳定、确认无残留影响）后才归档。避免自动归档掩盖回滚未完全恢复的情况。

#### 4.4.7 全局暂停

`levee pause-all` 暂停所有进行中的 run，用于紧急情况（如全局故障）止血。pause-all 需高权限操作，留痕，恢复需逐个 resume 或 `levee resume-all`。

#### 4.4.8 补充操作

表：补充操作对照表

| 操作 | 命令 | 语义 | 权限 |
| --- | --- | --- | --- |
| 取消 | `levee cancel <run-id>` | 取消未开始批次，已开始批次按策略（等待完成 / 强制中断） | 发起人或管理员 |
| 重试 | `levee retry <run-id>` | 重试失败批次 | 发起人 |
| 单台重跑 | `levee retry-host <run-id> <host>` | 重跑批次内单台主机 | 发起人 |
| 克隆 | `levee clone <run-id>` | 基于历史 run 生成可编辑副本 | 有权限人 |
| 模板 | `levee new <template> --params k=v,...` | 基于模板实例化新 workflow | 有权限人 |
| 关联 | `levee link <run-id> --incident <id>` | 关联变更与 incident | 有权限人 |
| diff | `levee diff <run-id-a> <run-id-b>` | 对比两次 run 的参数与执行计划 | 有权限人 |

#### 4.4.9 失败语义五档

表：失败语义五档对照表

| 档位 | 含义 | 处理 |
| --- | --- | --- |
| retryable | 瞬时失败（如网络抖动），可重试 | 自动重试（默认 3 次） |
| manual_retry | 非瞬时但可重试（如目标机临时不可用） | 不自动重试，等待人工 retry |
| rollback | 失败需回滚（如 SLO 门禁失败） | 触发自动回滚 |
| escalate | 失败需人工介入（如回滚失败） | 升级告警，停止自动动作 |
| fatal | 不可恢复（如快照损坏、审计写入失败） | 紧急告警，停止所有自动动作 |

### 4.5 D5 编排

#### 4.5.1 批次一等公民

批次在 LEVEELang 中是一等原语，不是用 `serial: 1` + `when` 模拟的二级特性。批次有显式边界、批次间门禁、批次级暂停 / 恢复、批次级回滚。

#### 4.5.2 DAG

workflow 内步骤按 DAG（有向无环图）编排，支持并行 + 依赖声明，不支持循环（循环用批次 + 重试表达，避免无限循环）。

#### 4.5.3 原生原语

LEVEELang 提供原生原语，非模板字符串：

- `batch`：批次声明。
- `gate`：门禁声明。
- `rollback`：回滚声明。
- `pause` / `resume`：暂停 / 恢复。
- `parallel` / `sequence`：并行 / 串行。
- `try` / `catch`：步骤级错误捕获（catch 内只能声明 rollback 或 escalate）。

#### 4.5.4 互斥锁 TTL

同一目标机同时只能有一个 workflow 在 apply。互斥锁通过分布式锁（集群形态）或本地锁（单机形态）实现，带 TTL（默认 1h，避免持锁进程崩溃后死锁）。锁过期后其他 workflow 可抢占，但抢占前需检查目标机状态确认无残留变更。

### 4.6 D6 双触发（简化）

#### 4.6.1 计划触发

`levee schedule` 按 cron 表达式定时触发 workflow，用于常规变更窗口（如每周六 02:00 打补丁）。

#### 4.6.2 webhook 触发

外部系统（如 ArgoCD sync 完成、Prometheus 告警、ITSM 工单状态变更）通过 webhook 触发 workflow。webhook 带签名校验，避免伪造触发。

#### 4.6.3 自愈默认关

自愈（基于告警自动触发修复 workflow）默认关闭。开启需显式声明，且自愈 workflow 仍走完整审批闭环（紧急审批通道），避免自愈误触发扩大变更半径（对应 2.3 腾讯 AIOps 复盘）。

---

### 4.7 D7 可观测与审计

#### 4.7.1 变更审计

每次 apply 产出完整 trace：

- 每个动作的输入、输出、耗时、目标机上下文。
- 哈希链：每个动作的 hash 包含前一个动作的 hash，形成链式结构，任何中间篡改都会断链。
- WORM 存储：trace 写入一次写多次读存储，不可篡改。

#### 4.7.2 哈希链分片

单次 run 动作量大时，哈希链按批次分片，每批一个子链，子链根 hash 串入主链。避免单链过长影响验证性能。

#### 4.7.3 变更-告警关联

LEVEE 变更 trace 与外部告警系统（Prometheus / Alertmanager）关联：变更时间窗口内的告警自动打上 `levee_run_id` 标签，便于复盘时定位"是不是这次变更引起的"。

#### 4.7.4 效能数据导出

变更效能指标（成功率、耗时、回滚率、门禁失败率）按 workflow / 模板 / 团队维度聚合导出，供 SRE 平台消费。

### 4.8 D8 安全与集成

#### 4.8.1 凭据代理

LEVEE 不直接持有目标机凭据，通过凭据代理（如 HashiCorp Vault、CyberArk、自研 4A）按需获取，用完即弃。凭据不落盘、不进 trace、不进日志。

#### 4.8.2 兼容逃生舱

为降低迁移成本，LEVEE 提供兼容逃生舱：

- 兼容层：可导入现有 Ansible playbook 执行，包一层审批 / 门禁 / 审计。
- 风险：兼容层不享受 LEVEELang 的类型安全与编译期检查，作为过渡使用，不推荐长期。

#### 4.8.3 兼容层风险评估

兼容层在每次执行前做风险评估：

- playbook 是否含 `shell` / `command` 等非幂等模块。
- playbook 是否含 `ignore_errors: yes`。
- playbook 是否无对应 rollback。

命中风险项标记为高危，强制升高审批级别。

#### 4.8.4 集成矩阵

表：集成矩阵对照表

| 集成对象 | 集成方式 | 用途 |
| --- | --- | --- |
| ArgoCD / Flux | webhook 互触 | 云原生层与非云原生层联动 |
| Prometheus | query + label | SLO 门禁、变更-告警关联 |
| Vault / CyberArk | 凭据代理 | 凭据治理 |
| ITSM（ServiceNow / Jira） | API | 工单驱动审批、审批留痕同步 |
| 堡垒机 / 4A | 通道插件 | 穿越堡垒机执行 |
| Slack / 飞书 / 钉钉 | webhook | 通知 |
| ELK / Loki | log export | 变更日志归档 |

#### 4.8.5 凭据轮换

凭据代理侧轮换，LEVEE 不感知轮换周期。LEVEE 仅在凭据获取失败时按 R7 产出结构化失败，不缓存旧凭据。

### 4.9 D9 通知与协作

#### 4.9.1 对象分级

表：通知对象分级对照表

| 对象 | 通知场景 |
| --- | --- |
| 发起人 | plan 完成、审批结果、apply 进度、apply 完成、回滚触发、回滚完成 |
| 审批人 | 待审批、审批超时预警、驳回后重提 |
| oncall | 紧急审批、回滚失败、fatal 错误 |
| 订阅人（团队） | run 完成、run 失败 |

#### 4.9.2 触发点

通知触发点贯穿闭环：plan 完成、审批待处理、审批通过 / 驳回、批次开始 / 完成、门禁失败、回滚触发 / 完成 / 失败、归档。

#### 4.9.3 渠道

支持 Slack / 飞书 / 钉钉 / 邮件 / webhook，可按触发点 + 对象配置渠道偏好。

#### 4.9.4 回滚通知

回滚触发必通知发起人 + 审批人 + oncall，回滚结果（成功 / 部分成功 / 失败）单独通知，不与 apply 通知合并，确保回滚可见性。

## 第5章 工作流 DSL（LEVEELang）

### 5.1 设计理念

LEVEELang 的设计理念：

1. 类型安全：编译期检查，运行期不做隐式类型推断。
2. 原生原语：批次、门禁、回滚是一等原语，非模板字符串。
3. 可读性优先：语法贴近运维心智，不追求图灵完备。
4. 模块化：workflow 可声明 input / output，跨 workflow 调用走显式接口。
5. 编译期可分析：编译为 IR，编译期可做影响面分析、冲突检测、plan 哈希锁定。

### 5.2 代码示例

代码示例：数据库 schema 变更（LEVEELang）

```leveelang
workflow db-migrate-orders {
  input {
    table: string          # 待迁移表名
    batch_pct: percent = 10%  # 首批百分比，默认 10%
    grace_period: duration = 5m  # SLO 门禁 grace period
  }

  target {
    type: "mysql"
    query: "role=primary AND cluster=orders-db"
    # 动态目标集在 plan 阶段物化并锁定
  }

  window {
    start: "02:00"
    end:   "04:00"
    timezone: "Asia/Shanghai"
  }

  batches {
    # 按主库分批，每批一个主库（避免多主库并发 DDL）
    strategy: "one-per-target"
    gate post_batch {
      slo {
        query: "rate(mysql_errors_total[5m]) < 0.01"
        source: "prometheus"
      }
      cmd {
        run: "mysqladmin ping -h {{target.host}}"
        expect_exit: 0
      }
    }
  }

  approval {
    level: high    # schema 变更属高危
    min_approvers: 2
    exclude_initiator: true
    timeout: 4h
  }

  step migrate {
    action: "mysql.pt-online-schema-change"
    args {
      host: "{{target.host}}"
      table: "{{input.table}}"
      alter: "ADD COLUMN status VARCHAR(32) DEFAULT 'active'"
    }
    requires_reboot: false
    irreversible: false
  }

  rollback {
    # 白名单回滚：pt-online-schema-change 自带 --reverse 语义
    strategy: "snapshot"
    on_failure: "auto"
    verify_after: true
    step undo_migrate {
      action: "mysql.pt-online-schema-change"
      args {
        host: "{{target.host}}"
        table: "{{input.table}}"
        alter: "DROP COLUMN status"
      }
    }
  }

  gate post_apply {
    slo {
      query: "rate(mysql_errors_total[{{input.grace_period}}]) < 0.01"
      source: "prometheus"
      wait: "{{input.grace_period}}"
    }
  }
}
```

该示例展示了一个完整的数据库 schema 变更 workflow，包含：

- 类型化 input 声明。
- 动态 target 查询。
- 变更窗口约束。
- 按主库分批 + 批次间 SLO 与命令门禁。
- 高危审批（2 人审批，排除发起人）。
- migrate 步骤。
- 白名单回滚（带回滚后验证）。
- post_apply SLO 门禁含 grace period。

表：6 层架构对照表

## 附录A 与原 OpsChain 设计的差异

LEVEE 在原 OpsChain 设计基础上做了精简与聚焦，主要差异：

1. 定位聚焦：从"通用运维编排"聚焦到"非云原生基础设施变更流水线"，明确不管 K8s 集群内。
2. 语言重做：从 YAML + Jinja2 转向类型化 DSL LEVEELang，编译期类型检查。
3. 通道重做：从依赖 Ansible SSH 转向插件化通道抽象，支持 SSH / WinRM / Agent / 厂商 API / 交互式。
4. 闭环强化：plan 哈希锁定、SLO 门禁三段时序、回滚协议显式化、失败语义五档。
5. 状态简化：不做主动漂移检测，只读漂移报告 + 显式 remove / unmanage。
6. 双触发简化：自愈默认关，避免误触发。
7. 部署形态明确：单二进制零依赖（MVP）→ 集群（V1）→ 气隙（V2）。
8. 兼容层引入：兼容逃生舱降低迁移成本，但独立模块不污染核心。
