# v1.17.0 Release Notes

**Release Date**: 2026-10-03

## Overview

The one remaining cross-system item — "OpsMesh-side service-addressing
semantics for the topology/metrics pull direction" — is resolved by reading
the platform's own source instead of guessing: the pull direction is now
wired end to end against the platform's **real** contracts. Per-item detail
in [CHANGELOG.md](../../CHANGELOG.md).

## The Addressing Question, Settled by Evidence

The integration design's §6.3 sketch (`GET /api/v1/topology?service=`) was
never implemented platform-side. Verified against the platform source
(`F:\Nexus\OpsMesh`):

- topology: `GET /api/v1/catalog/topology?tenantID=` — the asset/service
  catalog graph (nodes carry type/status/metadata/children; edges carry a
  relationType);
- metrics: `POST /api/v1/prometheus/query {"query": q}` — a PromQL
  pass-through evaluated at the instant of the call;
- health: `/healthz`.

All three of LEVEE's client methods now speak these contracts — the previous
revision modeled invented shapes that would have 404'd against a real
deployment.

**host → service needs no platform-side change**: the catalog returns the
whole tenant graph, and matching happens client-side through the existing
`topology.FindNode` (ID / name / endpoint / metadata-value containment — a
hostname or an IP in any metadata value matches; the adapter deliberately
does not guess which metadata key holds it).

## Pull Direction Wired

- The diagnosis impact-radius stage gained `provider: opsmesh`
  (`diagnosis.topology.tenant_id`, riding the `opsmesh.*` connection
  settings).
- Two read-only operator commands: `levee opsmesh topology [--tenant]
  [--service]` (with impact-radius analysis) and `levee opsmesh metrics
  --query <promql>`, both human-readable and `--json`.

## Platform Gap, Recorded Honestly

The result-report direction's `/api/v1/alerts/{id}/resolution` endpoint does
not exist platform-side yet (only `{id}/ack` and `{id}/silence`): reporting
against such a deployment logs a non-fatal 404 warning. Substituting `ack`
was considered and **rejected** — it carries no outcome payload and it
suppresses the platform's own escalation semantics; an automation silently
acknowledging alerts is a platform-side policy decision that must not be made
unilaterally from this client. The reasoning lives in the client's comments
and the config example.

Node `status` (the catalog graph's only health signal — it carries no traffic
metrics) is rendered into the impact-radius finding as `name[status]` for the
pivot and its neighbours.

## Upgrade Notes

- `diagnosis.topology.provider: opsmesh` requires `opsmesh.enabled=true` and
  `base_url`; a missing dependency degrades with a warning (the stage stays
  off) rather than blocking startup.
- `levee opsmesh` both subcommands are read-only and need no local store.
