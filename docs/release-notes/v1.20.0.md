# v1.20.0 Release Notes

**Release Date**: 未切版 —— 本文件先行登记内容范围；tag `v1.20.0` 切出并把 `Chart.yaml`
的 appVersion 与 `values.yaml` 的 `image.tag` 一起对齐后，此行替换为真实切版时间。

## Overview

v1.19.0 之后的第二批，共 **14 个小节**。前半批是"能不能直接交付"剩下的那几刀：命令门禁第一次真正
生效、手动回滚的结局可判读、chart 默认值指向真实存在的镜像 tag、CI 门禁的可信度。后半批是**新增
能力**：`human` 门禁第一次有了传输与 quorum、`policies.yaml` 进入服务层判定、五个非变更服务的 23 个
RPC 接上权限矩阵、以及 master 端 Agent 注册表 RPC。

**本稿原名 `v1.19.1`（随 #77 登记），现改叫 v1.20.0**：登记时 master 上只有前半批那五批修复与门禁
工作，之后落进来的是能力而非缺陷，按 semver 属 minor。`v1.19.1` 从未切版，registry 里也没有那个制品，
所以改名不收回任何对外承诺。逐条细节见 [CHANGELOG.md](../../CHANGELOG.md)。

## Behaviour changes (read first)

1. **命令门禁第一次真正生效**（#74）。此前引擎构造 `GateInput` 时从不供通道，任何声明了
   `cmd` 门禁的变更都在门禁处失败关闭 → **必然回滚**。现在按 `GateInput.TargetIDs` 逐台执行，
   判定规则是：**每台都要过**、**连不上算失败**（不是跳过）、**目标列表为空则失败关闭**。
   后果：升级后这类工作流可能从"必回滚"变成"按真实退出码放行"。如果某条命令在其目标上本来就
   通不过，结局不变（仍回滚），只是原因从 `missing_channel` 变成真实的退出码/stdout 不匹配。
2. **`RollbackChange` 不再把领域结局抛成 `codes.Internal`**（#72）。手动回滚"补不全"现在是
   一次可判读的结果：`success=false`、run 状态推进到 `rollback_incomplete`、已恢复的主机照常
   上报、消息带原始原因；真正的服务端故障仍然返回 `Internal` 且不改写历史。客户端从此可以按
   "该重试 / 该放弃 / 无事可做"分流，而不是对一个业务结局做无意义的 gRPC 重试。
3. **`probe` 的 `mode: remote` 与 `kind: script` 同样按目标逐台执行**（#76，与 #74 同规则）。
   `examples/gate-templates/{mysql,redis}.yaml` 里那两条远程 tcp 探针第一次可达。
4. **`human` 门禁在 serve 下第一次可用**（#83）。此前 `WithGateApprover` 生产 0 调用点，计划期
   直接以 `ErrGateNotExecutable` 拒绝——任何声明 `human` 的 workflow **根本 plan 不出来**。传输
   的做法是**复用审批链**：门禁打开时按确定性 ID `gate-<run>-<gate>` 建一条审批记录，等到有人决定
   并把决定与审批人身份回给门禁；门禁记录绑一个 run 永远不可能有的 PlanHash，因此批准门禁**不会**
   结算变更，反之批准变更也顶不开门禁。重启/续跑的门禁重挂到同一条记录而不是叠第二条。
   决定面是新 CLI `levee gate approve|reject <run-id> <gate-name>`，它刻意**不结算 run**（run 已在
   跑，门禁只是其中一步）。
   **迁移说明**：装了 `--engine-enabled` 的 serve 从此会安装门禁传输——声明 `human` 的 workflow
   由"计划期被拒"变为"可计划、运行到门禁时等待人在环"；等不到人时按该门禁的 `timeout_seconds`
   （缺省 1800s）超时失败。需要人工介入的部署要确保有人值守 `levee gate approve`。
5. **门禁的 quorum 与四眼原则**（#84）。工作流可声明 `min_approvers`（需要几个**不同的人**同意）
   与 `exclude_initiator`（禁止 run 的发起人投这一票）。两条参数此前都是**未知参数**（strict 校验
   fail-closed 拒绝），所以这是纯新增，没有存量工作流受影响。判定 fail-closed 的两处：声明了
   `exclude_initiator` 但 run 没有记录发起人时直接拒绝（`unverifiable_independence`），不把
   "无人可排除"悄悄降级成"谁都能投"；`min_approvers <= 0` 是参数错误。quorum 下审批人记录列出
   **全部**同意者，不只报最后一票。
   > 更正一处：#83 的小节末尾写着"未做：门禁的 quorum / `min_approvers` 与 `exclude_initiator`"，
   > 那是它当时的状态，**已被 #84 做完**。这里按现状登记，避免折叠后的 CHANGELOG 自相矛盾。
6. **审批决定现在携带可验签的审批人身份**（#82）。`verify.HumanApprover.RequestAndWait` 原先只返回
   一个 `bool`，于是即使装了传输，门禁结果里也不会有人名——审计只能记"approved"，记不了"谁批的"。
7. **`policies.yaml` 从此约束服务层判定**（#81）。此前这份文件只有 `levee rbac` 在算，服务层
   `authz.Decide` 从不读它。现在 `authz.Load` 读 `<dataDir>/policies.yaml`（缺失=正常；
   **解析失败=启动失败**，与 `permissions.yaml` 同姿态），并在矩阵与角色两轴都放行之后再跑一道
   策略层，**只收窄、绝不能放宽**。写了 `policies.yaml` 但过去只被 CLI 计算的部署，升级后服务层的
   可见范围会按策略收窄。
8. **五个非变更服务的 23 个 RPC 接上权限矩阵**（#51，安全修复）。此前 `target / inventory /
   template / audit / system` 只受认证约束——写了 `permissions.yaml` 想把 dev 队挡在 prod 外的
   部署，实际上只把**一半 API** 交给了策略：同一调用方仍能枚举全部 prod 主机及其 `credential_ref`、
   冻结或退役一台 prod 主机（`SetTargetStatus`）、批量导入清单、删掉别队赖以创建变更的模板、读整条
   审计链与任意 run 的报告（`TargetHistory` 还会交出每个触及该主机的 run 的工作流全文与创建者）、
   导出部署配置（`GetConfig`）。姿态集中在 `internal/grpc/resource_authz.go` 一处：**fleet 写要
   `admin`**，**读按 `view`**，且列表是**收窄**而不是整页拒绝；无可归因主体（共享令牌）仍可读、
   不可写。环境的取自资源自身声明（target 的 `labels["env"]`、run 的环境列），分组/模板/配置不声明
   环境，故落在 `permission.default_env`，没有 default 时**拒绝而不是猜**。

## New capability: 跨进程可见的 Agent 注册表（#85）

注册表不再住在"构造它的那个进程"里：daemon 把它落在自己的 store（`agents` 表，schema v8 前向迁移，
SQLite 单机 / PostgreSQL 集群），并经 gRPC `AgentService` 供数；`levee agent list|show|remove
--remote` 读的就是这张表。跨进程可见性不是靠推理——测试二进制以**子进程**重执行自己、独立打开同一个
SQLite 文件读注册表，逐项断言 注册 → 心跳 → daemon 重启 → 删除 四条腿。

三条值得单独讲的取舍：

- **列归属写死在 SQL 里**：re-register 不许改 `registered_at`（重注册不该让 agent 变年轻），也不许
  碰 `last_heartbeat`（那列归心跳所有）。一列两个写主正是"谁赢了"这类竞态的来源。
- **状态词表被校验而非透传**，只接受 `registered | idle | busy | offline`；心跳的状态缺省按负载派生
  （复用 `agent.DeriveStatus`，避免出现第二份手写判据）。收下任意字符串等于允许一个拼写错误把 agent
  永久停在"看起来健康"。
- **没有 store 就回 `Unimplemented`，绝不回一张空表**。"没有注册表"与"注册表里恰好没有 agent"必须
  可区分——后者正是这次要消灭的那个谎言。

**新的部署要求**：注册表的四个写 RPC（注册/心跳/注销/移除）与 `AddTarget` 同一条姿态，需要 `admin`；
两个读 RPC 需要 `view`。所以**装了权限矩阵的部署里，用共享令牌（无可归因主体）的 agent 会被拒写**，
要给它一个可归因、且持有 admin 的身份。

`agent start` 仍留在进程内：proto 里没有 master→agent 的任务流 RPC，把生命周期切过去只会得到一个
"注册成功、然后永远等不到派发"的 agent。

## Delivery-artifact fix

**chart 默认值此前拉取一个 registry 上不存在的镜像 tag**（#73，v1.18.0 起如此）。
`release.yml` 推的镜像 tag 就是 git tag 名（带 `v`），而 `values.yaml` 写的是不带 `v` 的版本号，
于是 `helm template` 渲染出 `ghcr.io/levango7/levee:1.18.0` —— 实测该 manifest 返回 404，而
`v1.18.0`/`v1.19.0` 返回 200。按默认值执行 `helm install` 的客户会落在 ImagePullBackOff。

- 切版时 `values.image.tag` 与 `Chart.appVersion` 一起对齐到本版（`v1.20.0` / `1.20.0`）；
  在 tag 真正切出之前，chart 仍指向上一个真实存在的发布拼写——版本门禁规则②要求 image.tag
  逐字存在于 tag 集合，抢先写未来版本号会让 `delivery` job 直接变红（这正是该门禁该做的事）。
- **已发布的 v1.19.0 快照不受影响**（tag 不可变）：从那个 tag 部署仍需
  `--set image.tag=v1.19.0`，`docs/release-notes/v1.19.0.md` 已写明。
- 交付门禁 `scripts/check_release_versions.py` 规则②改为**字面**校验 image.tag（不再自己合成
  `v` 前缀），规则①按版本号比较；并给它补上自测 `scripts/test_check_release_versions.py`。
  这一族缺陷的根因值得留档：门禁全绿，是因为它在校验一个自己合成出来的命题。

## CI gate credibility

- **冒烟脚本不再冒充健康检查失败**（#75）：端口被别的进程占用时，`scripts/smoke_serve.sh`
  以前报 `/healthz never became reachable`，把读者送去查一个不存在的 bug。现在启动前先逐端口
  探测并点名归属与占用者。顺带修掉每次成功运行都泄漏一个临时目录的 trap。
- **版本门禁有了自己的测试**（#73）：`release-gate` job 改为 `unittest discover`，并逐套件点名
  收集结果——空收集会以 `Ran 0 tests / OK` 静默通过。
- **版本门禁规则③的盲区补掉**（本批折叠 CHANGELOG 时暴露）：`未切版` 标注原先按"正文里出现即可"
  判定，于是把旧版本"撤掉未切版标注"的留痕折进新版本小节，就等于替一个未标注的新小节白送一个通过。
  现在只认**行首的声明行**（`> 未切版` 或 `> **发布状态：未切版。**`），并加了两条回归用例；
  另在真实文件上反向验证：删掉声明行、保留无关散文，门禁确实变红。
- **结构守卫**（#76）：`internal/engine/gate_input_channel_provider_test.go` 要求引擎每一处
  `verify.GateInput` 都填 `ChannelFor` 且不得预拨单通道；扫描命中数低于 4 处即判红。
- **聚合门禁把"没有判定结果"和"失败"分开说**（#78）：runner 池饥饿时 job 会在排队中被取消
  （实测 `runner_name=""`、`steps=[]`），而聚合步骤原先只报 `FAILED`，于是"一次红"被读成
  "一次回归"。现在按结论分桶：`failure` 仍是 `FAILED`，`cancelled/skipped/neutral/timed_out/stale`
  归为 `UNVERIFIED, not failed … Re-run this workflow before reading it as a regression`——
  **仍然退出 1**，只是不再谎报原因。并给这段 bash 本身补了 CI 内自测
  `scripts/test_ci_aggregate.py`（5 例：全绿、真失败、排队超时、`neutral/stale` 归桶、清单漂移），
  逐字从 workflow 里取出被验文本，所以改坏它当场变红。

## Known gaps after this snapshot

- `probe` 的 remote **http** 不展开 `{target}`（direct 会展开）；刻意保持现状并写进
  `docs/gates.md`，统一与否属界面一致性决策。
- `POST /gates/verify` 的 ad-hoc 检查仍不为 `probe` 类型拨号，远程探针经该端点仍失败关闭
  （改动它等于让一个 HTTP 端点按需登录目标机执行命令，属权限面决策）。
- Agent 侧的**任务下发通道**仍不存在（proto 无 master→agent 流），因此 `agent start` 是进程内的；
  本版本交付的是注册表契约 + 持久化 + 运维可见性。
- `agents` 表没有环境列，因此权限矩阵对 agent 的判定落在 `permission.default_env`，不是按 prod/staging
  分环境收窄。要做分环境收窄得先定 schema，不能在前端或 CLI 里靠命名猜。
- Web UI P0（变更详情页 / 审批中心卡片 / `/monitor` 三视图联动）未做，且已核实其依赖不是"只差 UI"：
  已记录的**门禁结论**与**审批历史**没有读路由，`GET /changes/{id}?includePlan=true` 是被解析转发
  却被 `GetChange` 忽略的**死参数**；`WatchChange`/`StreamLogs` 只有 gRPC 流、没有 REST/SSE 路径。
  另记一条事实供后续修正：`MonitorView` 当前的门禁卡是**三行硬编码 `pending`** 的字面量，而
  `batches` 从未被赋值——看板在编造状态。
- 产品面其余未闭合项见 `docs/product-roadmap.md`。
